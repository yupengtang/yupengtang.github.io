--- title: "MCP-AgentGym: A Verifiable Gym for Post-Training Tool-Using Agents" excerpt: "A real Kubernetes control plane as a post-training environment: 36 typed MCP tools, 14 seeded fault families, and an executable verifier that computes rewards instead of grading them. Qwen3-8B trained with SFT, DPO and GRPO, served through vLLM, measured on 11,541 verified trajectories." collection: portfolio ---

Post-training an agent needs thousands of episodes that reset cleanly, run in parallel, and pay out a reward you can compute rather than grade. A real Kubernetes cluster gives none of that. Episodes take minutes, never reset to the same state twice, and the same action can produce different outcomes on different runs, which breaks DPO preference pairs and GRPO advantages alike.

MCP-AgentGym splits the stack at the API boundary, which is where an agent operates anyway. The control plane is real: etcd, apiserver, controller-manager and scheduler run as unprivileged user processes, so CRDs, RBAC, admission and the whole Deployment to ReplicaSet to Pod reconcile path behave as they do in production. The kubelet is replaced by a deterministic workload simulator, so pod status is a pure function of declared state. Incidents come from a seeded catalogue of 14 fault families, the agent works them through 36 typed MCP tools, and an executable verifier reads live cluster state to decide whether the incident was actually fixed. No model judges anything.

The result is what post-training actually needs: sub-second resets, hundreds of parallel episodes per node, zero GPU cost for the environment itself, and rewards that are computed from cluster state rather than assigned by a judge model. Correctness is not assumed. For all 14 fault families there is a test asserting that the injected fault provably breaks the cluster and the known-correct remediation provably fixes it, with the verifier recognizing both states.

What post-training bought, and what it cost

Evaluation uses 5,000 incidents with zero id overlap with training, 2,200 episodes per arm, and a Bonferroni threshold of z > 3.0 for the comparisons reported.

Incident resolution rate. n = 2,200 per arm.

Training bought 16.2 points of resolution (z = 10.96), 14.2 points of root-cause accuracy (z = 9.57), and cut invalid tool calls from 26.3% to 0.3%, a factor of about 100. It cost 27.6 points on fault families never seen in training (z = 19.06). Both sides clear significance by a wide margin, and both are far larger than any difference between the post-training methods themselves. The untrained model is the best agent in this project on families it was never trained for, and the worst everywhere else.

The mechanism is measurable, and it decides the fix. Fine-tuning drives the two never-demonstrated diagnosis labels to 0 emissions across 599 submissions, against 25 of 501 for the base model. Both labels sit in the submit_diagnosis enum and in the system prompt on every episode, so the models are not blind to them. They can no longer reach them, and what they emit instead is confidently wrong and drawn from the training catalogue. That is label-prior collapse rather than degraded reasoning. Degraded reasoning would call for better data; a collapsed prior calls for attenuating the update.

Reversing the trade at serving time

A LoRA update enters each layer as ΔW = (α/r)·B@A, so scaling lora_B by s scales the update exactly. At s = 0 the model is the base; at s = 1 it is the trained one; everything in between is servable from a single engine by multi-LoRA.

The recovery is monotone at every step, both adjacent comparisons are significant (z = 3.55 and z = 2.22), the end-to-end effect is z = 5.97, and there is no measurable in-distribution cost (67.2% against 65.6%, z = 0.27). It also replicates on a second, independently trained adapter family to within 1.6 points: the SFT adapter recovers from 35.8% to 70.0% (z = 5.65). Two policies trained with different objectives on different data collapse the same way and recover the same way, which points at update magnitude rather than anything specific to one checkpoint. One knob, applied after training has finished, moves a served model along the specialization axis.

The variance budget

Before any method comparison can mean anything, the noise floor has to be measured. Same evaluation pool, same n.

DPO on baseline B−0.27 pp−0.18
Nondeterminism, same seed−0.18 pp−0.12

Tuning the learning rate mattered more than every post-training method tested, by a margin nothing else approaches. The seed floor is 3.1 points, which is the same size as DPO's measured effect, and that is why the same DPO recipe helped substantially on one baseline and did nothing on another when both were identically configured and scored within 0.2 points of each other. There are two floors here: 0.2 points between two runs of the same configuration, and 3.1 points between independently trained models. Method comparisons are the second case, and using the first understates the relevant noise by a factor of sixteen.

The best agent in the whole grid is a plain supervised fine-tune that happened to train at the better learning rate, at 57.7% resolution and 0.01% invalid calls. It beats every post-trained variant. That top row is not a post-training result, it is the absence of one.

Serving

One L40S, Qwen3-8B, with the real 36-tool system prompt. The synthetic conversation deepens exactly as an episode does, so the shared prefix grows while new tokens per turn stay small.

32 concurrent requests. Throughput at 20 turns goes from 0.26 to 4.67 req/s, an 18× gain.

Cost per unit of prompt tells the same story: uncached, milliseconds per 1k prompt tokens stays flat at about 3,800 because every turn re-reads the whole conversation, while cached it falls from 870 to 300. Prefix caching does not merely help an agent workload, its benefit compounds with conversation depth, which is the defining property of one. On multi-LoRA, the SFT adapter serves at 1,075 ms p50 against the base model's 2,292 ms, and that 2.1× gap comes from behavior rather than the engine: the adapter emits a short tool call where the base emits a long thinking block.

Guardrails

The same discipline that produced the results above retracted five of this project's earlier claims, including one that had been published, was contradicted by a later run, and was withdrawn with its trajectories quarantined rather than deleted.

"DPO +8.2 pp"
Was +2.1 pp under power and never significance-tested when first published. Winner's curse.
"Preference pair count matters"
A 437-pair replication scored identically to the 88-pair run.
"Episode-GRPO damages tool-call format"
The adapter had been initialised two versions behind its own training data.
"Seed variance is 15.6 pp"
It was the learning rate. No launcher ever forwarded --seed, so every adapter the project produced had trained at seed 0.

Those defects are now asserted against in code rather than described in prose. The report script refuses to render a partial grid. One test checks that every tool count quoted in the documentation matches the registry, another that the serving numbers are recomputable from their raw artifacts, and another that every result-bearing argument a trainer accepts is actually reachable from its launcher, which is the test that would have caught the seed bug. Training records a weight digest of its base adapter so lineage is checkable, which is how the withdrawn GRPO run was found. The dataset builder refuses to overwrite the corpora the published results were trained on.

The worst bug in the project is why a prompt-contract suite exists at all: tool schemas were being passed as an API field that the project's own chat template ignored, so the model was asked to call tools it had never been shown, and nothing raised. It would have silently voided both the base-model comparison and the entire schema-shift result. The invariant is now asserted: whatever the gateway presents must be literally present in the text the model receives.

What this does not establish

  • Whether DPO helps, as a number. With the learning rate matched and the floor measured, two identically configured baselines gave +4.18 pp (z = 2.83) and −0.27 pp (z = −0.18). The floor is 0.2 pp and the first effect is twenty times that, so the variability is in training rather than measurement. DPO can help by a wide margin; a number cannot be quoted.
  • Any ordering among SFT, DPO, episode-GRPO and action-GRPO. Each was trained once, so their differences sit inside the spread one recipe produces by reseeding.
  • Anything about a second base model. Everything here is Qwen3-8B.
  • Live cloud behavior. The S3 artifact store is asserted against moto and the Helm EKS overlay renders and is diffed in tests, but neither has been run against a real account.

What I took away

Two things transfer beyond this environment. The first is that a closed training catalogue buys in-distribution skill and sells out-of-distribution coverage, and that the exchange rate is measurable, mechanistic, and reversible at serving time rather than a vague risk to warn about. The second is that most of what looked like method effects was infrastructure: a learning rate, a seed that no launcher forwarded, a chat template that silently dropped the tool schema. Measuring the noise floor before comparing methods is not extra rigour, it is the difference between a result and a coin flip.
