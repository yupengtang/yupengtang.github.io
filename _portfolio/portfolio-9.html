CacheFlow is a from-scratch inference engine built in C++17 and CUDA 12, extending llama.cpp's autoregressive decode path to handle multiple concurrent requests efficiently. Stock llama.cpp processes requests sequentially — each request occupies the full KV cache until completion. CacheFlow replaces this with a batching-aware architecture modeled after vLLM's design, implementing every core subsystem independently: a preemptable scheduler, a block-based memory manager, paged attention CUDA kernels, and a trie-based prefix cache.

The project spans approximately 5,800 lines of C++ and CUDA, with six test suites covering each subsystem. The goal was to understand precisely why naive LLM serving is inefficient and to fix both root causes: sequential request processing and contiguous KV allocation that fragments GPU memory.

Root Causes of Naive Serving Inefficiency

Two independent bottlenecks make stock llama.cpp unsuitable for concurrent traffic:

  1. Sequential processing. One request at a time means GPU compute idles between the prefill of one request and the next. Continuous batching eliminates this by interleaving decode steps across active requests.
  2. Contiguous KV allocation. Reserving a maximum-context-length contiguous block per request fragments GPU memory quickly — a request using 512 of 4096 reserved tokens blocks the remainder. Even when physical memory is available, the allocator cannot serve a new request. Block-based management with logical-to-physical mapping solves this entirely.
These are the same two problems vLLM solves in Python. CacheFlow re-implements the same ideas in C++ at the llama.cpp layer, with hand-written CUDA kernels for the non-contiguous attention access pattern.

Scheduler

Continuous Batching with Preemption

The scheduler manages three queues: waiting (new requests pending prefill), running (active decode), and swapped (preempted, KV cache on CPU). At each decode step it:

Evict lowest-priority running sequences if memory is tight
→
Promote swapped sequences if blocks are available
→
Admit new requests from waiting queue
→
Dispatch batch to attention kernel

Three pluggable scheduling policies are implemented: FCFS (first-come-first-served for fairness), Shortest Remaining First (minimize average completion time), and Priority (external priority scores). All operate without synchronization barriers — sequences can be added or removed at every decode step.

Block Manager: Paged KV Cache

Fixed-Size Blocks with Logical-to-Physical Mapping

Each sequence maintains a block table — a mapping from logical block index to physical block index in GPU memory. The block manager allocates fixed-size physical blocks (default: 16 tokens each) on demand, so a 512-token sequence uses exactly 32 blocks rather than reserving 4096 tokens worth of contiguous space.

Two additional mechanisms handle advanced use cases:

  • Copy-on-Write (beam search). When a sequence forks (e.g., beam search creates multiple branches), child sequences share the parent's physical blocks with reference counting. A write to a shared block triggers a copy, isolating the branches without duplicating unmodified prefixes.
  • Reference counting for reuse. Blocks at reference count 1 can be returned to the free pool immediately on sequence completion, eliminating fragmentation over time.
Block-based management is what enables 88% GPU cache utilization at peak concurrency. Contiguous allocation would fragment to unusable levels well before that point.

Paged Attention CUDA Kernels

Standard attention kernels assume KV cache is contiguous in memory. With paged allocation, keys and values for a single sequence are spread across non-contiguous physical blocks. Two custom CUDA kernels handle this:

V1 — Warp per Query Head
One warp handles the full attention computation for one query head: it iterates over the block table, loads keys and values block by block, and accumulates the attention output. Effective up to ~8K context length where the per-warp iteration cost stays bounded.
V2 — Partitioned with Log-Sum-Exp Reduce
Partitions the sequence dimension across multiple thread blocks. Each partition computes a partial softmax; a final reduction pass merges partial results using the log-sum-exp identity for numerically stable combination. Scales to 32K+ context lengths where V1 becomes a bottleneck.

Both kernels navigate the block table at runtime, converting logical token positions to physical memory addresses during attention computation. The switching heuristic: use V1 when sequence length ≤ 8192 tokens, V2 beyond that.

Prefix Cache

Trie-Based KV Reuse with LRU Eviction

Many LLM deployments share a common system prompt across all requests. Without prefix caching, each request re-runs the prefill computation for those tokens. The prefix cache stores completed blocks from past requests in a trie indexed by token ID sequences. On a new request:

Tokenize prompt
→
Walk trie to find longest cached prefix
→
Copy matched physical blocks into new sequence's block table
→
Run prefill only on uncached suffix

Cache eviction uses LRU policy: the least-recently-used blocks are freed first when the cache is full. In workloads with a fixed system prompt, this eliminates the full prefill for every subsequent request — measured at roughly ~50% prefill time reduction.

Defragmentation Kernel

Over time, as sequences of varying lengths complete and their blocks are freed, the active blocks of live sequences become scattered across non-contiguous physical addresses. This increases TLB miss rates and hurts memory bandwidth utilization during attention. A periodic compaction kernel migrates live blocks to a contiguous region, reducing the working set footprint and improving TLB locality without any change to the logical block tables visible to the scheduler.

The 1.8× throughput improvement over stock llama.cpp at 8 concurrent requests comes entirely from eliminating sequential request processing — the same GPU compute now serves multiple requests simultaneously rather than idling between them. The 34% reduction in latency variance over 10K-token generations comes from the block manager's ability to maintain high cache utilization without fragmentation-induced stalls.

The gap between 6.2× (8 req) and 9.1× (16 req) reflects batching efficiency gains: larger batches better saturate GPU compute during each decode step, raising arithmetic intensity above the memory-bandwidth-bound threshold for attention.

Profiling Infrastructure

A lightweight profiling layer instruments each serving component without modifying the hot path:

  • Time-to-First-Token (TTFT): measures prefill latency from request arrival to first generated token.
  • Time-per-Output-Token (TPOT): measures per-decode-step latency averaged across active sequences in the batch.
  • Chrome Trace export: emits a .json file compatible with chrome://tracing and Perfetto, enabling visual inspection of scheduler decisions, block allocation events, and kernel timings across the full request lifecycle.
